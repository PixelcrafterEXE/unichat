# Importing WhatsApp chat history from a local backup

WhatsApp only sends recent history to a linked device, so UniChat's WhatsApp archive starts (almost) at the moment of linking. This feature adds the history of an
**Android local backup** (`msgstore.db.crypt15`, plus the plain `Media` folder) to the **local archive** of an existing WhatsApp account. Nothing is sent to WhatsApp.
Code: `packages/core/src/whatsappimport/*`, UI `apps/ui/src/WhatsAppBackupImport.tsx` (button `#whatsapp-history` on the WhatsApp account card), RPCs `whatsappBackupInspect`, `whatsappBackupImport`, `whatsappBackupCancel`, progress `backup-progress` (ops `whatsapp-inspect`, `whatsapp-import`). It is modelled on the Signal import (docs/SIGNAL_IMPORT.md).

**Status: fixture-tested only.** No real WhatsApp backup was available. The container format follows the open-source wa-crypt-tools (ElDavoo); the msgstore.db schema follows community documentation. Treat the first real run as an experiment (use *Check the backup* first, it writes nothing).

## What you do on the phone (Android)
1. WhatsApp > Settings > Chats > Chat backup > **End-to-end encrypted backup** > Turn on > choose **Use 64-digit encryption key instead of password**. WhatsApp shows **64 digits** (hex: 0-9 and a-f). Write them down right then; UniChat needs exactly these. (This is only a local/Google Drive backup option; it does not change how your chats are encrypted on the network.)
2. Back on Chat backup: **Back up** (tick *Include videos* if you want them) and wait for it to finish. A manual backup writes `msgstore.db.crypt15` to the `Databases` folder of the WhatsApp data folder:
   `Internal storage/Android/media/com.whatsapp/WhatsApp/Databases/` (Android 11+; older phones: `Internal storage/WhatsApp/Databases/`). Media lives next to it in `.../WhatsApp/Media/` (WhatsApp Images, WhatsApp Video, WhatsApp Documents, WhatsApp Audio, WhatsApp Voice Notes ...; WhatsApp keeps these anyway).
   On Android 11+ the folder `Android/media/com.whatsapp` is visible from a USB file transfer or a file manager (not from "Android/data").
3. Copy the whole **WhatsApp** folder (it contains `Databases` and `Media`) to the computer/server that runs UniChat. If you only copy the one file, the import still works but without media.
4. In UniChat: Settings > Accounts > the WhatsApp account > **Import chat history**. Choose `msgstore.db.crypt15`, type the 64 digits, **Check the backup**, review, **Import history**.
   - Desktop app: the file dialog gives a path; the media folder is found automatically at `<WhatsApp folder>/Media` (two levels up from the file). If it was copied elsewhere, type the path of the `WhatsApp` folder in the *Folder with the media* field.
   - Server/browser: a chosen file is uploaded; media cannot be uploaded (thousands of files), so put the whole `WhatsApp` folder inside the backend's backup folder (`UNIMSG_BACKUP_DIR`, default `<data>/backups`) and type its path in the media field. File paths are only accepted inside `UNIMSG_BACKUP_DIR` (and only on loopback), exactly like the other backup features; the media files are read-only and never leave that folder.

crypt14 (older, no end-to-end encryption): opens only with the 158-byte `key` file from `/data/data/com.whatsapp/files/key`, which **needs a rooted phone**. UniChat asks for that file when it sees a crypt14 backup. Without root: turn on the encrypted backup above and back up again. crypt12 and older are refused.

## On the Android app: "Find the backup on this phone" (no copying to a computer)
When UniChat runs on the same phone as WhatsApp, the import page offers **Find the backup on this phone** (`apps/ui/src/SafBackupFinder.tsx`, native side `apps/android/.../node/SafImport.java`, bridge calls `$backupLocate` / `$backupCopy` / `$backupCopyCancel` / `$backupDiscard`, see `apps/android/src/bridge-protocol.ts`). It uses the **Storage Access Framework**, so UniChat needs no storage permission and never `MANAGE_EXTERNAL_STORAGE`:
1. The system folder picker (`ACTION_OPEN_DOCUMENT_TREE`, hint `EXTRA_INITIAL_URI` = `primary:Android/media/com.whatsapp/WhatsApp`) opens already in that folder; the user taps **Use this folder** and **Allow**. UniChat keeps a read-only persistable grant for that one folder (`takePersistableUriPermission`); later runs skip the picker. **Choose another folder** re-opens it.
2. UniChat lists `msgstore*.crypt15/14` (newest first, increments skipped) and the top-level `Media` folders with sizes (hidden `.`-folders skipped). Large folders (> 2 GiB) are unticked by default.
3. The chosen file and ticked media folders are streamed (1 MiB buffer, progress, cancel, resumable: files already copied with the same size are skipped, free space checked first) into `<data>/.backup/saf/whatsapp/WhatsApp/{Databases,Media}`: inside the backend's backup path policy and in the layout the importer's "Media next to the backup" discovery expects. The 64-digit key is typed as before. The copies are deleted after the import / *Start over* (`$backupDiscard`). The manual file chooser stays below as a fallback.
Requests carry file NAMES inside the located folder, never URIs. Nothing in the picked folder is ever written.

**Verified on a real phone (Samsung, Android 14 / SDK 34, One UI, 2026-11-15):** `Android/media/com.whatsapp/WhatsApp` (and `.../Databases`) is selectable in the system picker (the "Use this folder" button is enabled; `Android/data` is the part Android 11+ blocks); the in-app picker opened pre-pointed at it; the grant, listing (3 database files, 12 Media folders with real sizes), and a streamed copy of `msgstore.db.crypt15` (31 MB, SHA-256 identical to the original) plus 637 media files (150 MB) with live progress worked. Not verified: decrypting/importing the copied file (needs the user's 64-digit key, deliberately not used), copying multi-GB folders, grant survival across reboot.

## Format as implemented (crypt.ts)
```
file    = [u8 n][0x01 optional "feature table" flag][BackupPrefix protobuf, n bytes][AES-GCM ciphertext][tag 16][md5 16]
prefix  = { 1 key_type, 2 c14_cipher{ 1 cipher_version, 2 key_version, 3 server_salt, 4 google_id, 5 IV }, 3 c15_iv{ 1 IV(16) }, 4 info{ 1 app_version, 3 jidSuffix, 4 backup_version, ... } }
md5     = MD5 of everything before it; a "multifile" backup has none: the last 16 bytes are then the tag
cipher  = AES-256-GCM, 16-byte IV from the header, no AAD;  plaintext = zlib( SQLite database )
crypt15 = the 64 hex digits are a 32-byte ROOT key; AES key = HMAC-SHA256( HMAC-SHA256(key = 32 zero bytes, msg = root), "backup encryption" || 0x01 )
crypt14 = AES key = last 32 bytes of the 158-byte key file (27-byte Java serialisation wrapper + 131 bytes; checked: cipher version 0001, sha256(google id) == hashed id)
```
Pass 1 checks the md5 trailer (decides where the tag sits); pass 2 decrypts in 1 MiB chunks, the first plaintext byte must be a zlib header (else "wrong key", detected before the whole file is read), inflates into a private `0600` temp file in the backend's managed backup folder (`.import-wa-*.db`, removed in every case: success, error, cancel; leftovers are swept at start), and the GCM tag is verified at the end. Caps: decompressed size 48 GiB.

## What the importer does
1. **Authenticate/decrypt** (above). Wrong key, damaged, cut-off or non-WhatsApp files give plain-language errors. Memory use does not depend on the file size.
2. **Read the schema, tolerantly** (`reader.ts`, `node:sqlite`, read-only queries only): tables and columns are discovered with `PRAGMA table_info`; missing optional tables/columns mean "not available". Needed: `message(_id, chat_row_id, from_me, key_id, timestamp, message_type)`, `chat(_id, jid_row_id)`, `jid(_id, raw_string | user+server)`. The old pre-2022 `messages` layout and anything else without the core is refused as **"Unsupported schema: ..."** naming the missing piece.
3. **Map** (streamed in one ordered scan with LEFT JOINs; reactions, poll votes, vCards are small side tables loaded once).
4. **Write in ONE store transaction** with the same rules as the Signal import (`fillMissing`: never overwrite or delete; only missing text/attachments/reply/contacts/status/reactions are filled; a deleted message stays deleted). Cancel or any error rolls back messages, the chat list setting and the media written meanwhile. Then `reload()` rebuilds the search index; imported messages never touch unread counters, notifications or mesh relays.

## Mapping decisions
- **Chat ids** `<accountId>:<jid>` in the live provider's form: no device suffix, `@c.us` -> `@s.whatsapp.net`, groups `@g.us`. A `@lid` chat is folded into the phone-number chat using, in this order, the live connector's LID map (`Connector.importMaps().lidToPn`) and the backup's `jid_map` table; unmappable LIDs stay `@lid` and are reported as a warning.
- **Message id = WhatsApp `key_id`** (the id Baileys gives) so an imported message is the same row as a live/synced one. An edited message keeps `message_edit_info.original_key_id` (= the first revision's id); `editedAt` = last edit time.
- **Sender**: own messages use the account's own id (`importMaps().own[0]`, same as the provider's `selfId()`; remembered in setting `whatsappImport.identity.<account>`; a placeholder `me` + warning when the account never connected); DMs: the chat jid; groups: `sender_jid_row_id` (LID folded as above). Display names come from the number (`+49...`) because msgstore.db has no address book; the provider's names replace them in the UI where it knows them.
- **Content**: text (`text_data`; media caption), replies (`message_quoted`: stanza id, sender, preview), reactions (`message_add_on` + `message_add_on_reaction`, last per sender wins, empty = removed), deletes (`message_type` 15/64 or `message_revoked` -> `deleted`, text/media/reactions dropped), edits, forwarded (`message_forwarded`), disappearing (`message_ephemeral.duration` -> `expiresIn`; `chat.ephemeral_expiration` -> chat `disappearing`), locations and live locations (`message_location`), contacts (`message_vcard`: name, phones, emails, `waid`), polls (`message_poll_option`, votes from `message_add_on_poll_vote_selected_option`; a voter's latest vote replaces earlier ones; option ids = sha256 of the option text, as the live provider), view-once media (`viewOnce`, placeholder text, no bytes), status of own messages (13/14 read, 5 delivered, else sent).
- **Group names** from `chat.subject`; chats are kept in setting `whatsappImport.chats.<account>` and merged into the chat list by `Hub.collect()` (`withWhatsAppImportedChats`); a chat the provider already lists wins.
- **Noise counted, not imported**: `message_system` rows (counted as `system-<action_type>`: joins, renames, number changes, timer changes ...), calls (types 8/10/90), status/broadcast/newsletter chats (`chat-unsupported`), unknown `message_type` without text (`type-N`), empty rows. Shown as "skipped" counts in the inspect result.
- **Media**: `message_media.file_path` (relative to the WhatsApp folder, e.g. `Media/WhatsApp Images/IMG-...jpg`) is resolved inside the media root (symlinks resolved, anything leaving the root is ignored), `file_size` and `file_hash` (base64 sha256 of the plaintext) are verified; files that fail are counted as `mismatch` and not imported, absent files as `missing` (the message keeps a `[Photo]` / `[Voice message]` ... placeholder), files over 256 MB are skipped. Stored in the sealed media cache under the live key `<chatId>|<messageId>|a0` so the normal `attachment` RPC serves them offline. Voice notes (audio under `WhatsApp Voice Notes` or `.opus`) become `voice`, `message_type` 13 / `gif_attribution` GIFs play as GIFs, stickers keep their kind. **Not kept**: the media key / direct path (the live provider could use them to download files missing from the folder; not wired, see TODO).
- **Account check**: the backup header carries the last two digits of the phone number (`jidSuffix`); they are compared with the account's own number (match / mismatch / unknown). A mismatch or an unverifiable (signed-out) account needs an explicit confirmation, as in the Signal import.

## Security
The 64 digits (or key file) exist only in the RPC parameters and the derivation call: never stored, logged, or put in an event or error message. The root key and derived AES key buffers are zeroed after use (the hex string the UI sent cannot be wiped from the JS heap). Decrypted rows live in memory only until written to the sealed archive (AES-256-GCM at rest). The one plaintext artifact is the temp SQLite file described above (0600, deleted before the slow search re-index). No message content is logged. Uploaded files (browser) are removed through `backupDiscard`. Media files are only ever read, and only below the chosen media root.

## Verified vs not
- Fixture-tested (22 core tests, 10 e2e): our own writer implementing the documented container (crypt15 single-file and multifile, crypt14 + key file, raw SQLite payload), tamper/wrong key/truncation/cancel, synthetic msgstore.db with the schema below, merge rules, idempotence, rollback on cancel, 50,000-message stream.
- **Not verified without a real file**: header field numbers and the md5/tag trailer on current WhatsApp versions, the "backup encryption" derivation constant against a real key, every table/column name of msgstore.db (esp. `message_add_on*`, `message_poll*`, `message_system.action_type`, `jid_map`, `message_media.gif_attribution`), the `message_type` numbers, the `message_revoked` semantics, how WhatsApp stores edited-message ids, and that the Media paths in `file_path` match the folder layout of the copy. Schema drift shows as "Unsupported schema: ..." or as skipped counts in the inspect result.
- Android (nodejs-mobile, Node 18 + sql.js shim): untested; the reader needs `node:sqlite` (`DatabaseSync.prepare().iterate()`).
