# UniChat architecture (TypeScript everywhere)

```
apps/ui                 React UI (Discord-style: space rail | chat list | conversation)
apps/desktop            Electron – Hub runs IN-PROCESS in the main process, UI via IPC (Linux, Windows)
apps/android (todo)     Capacitor/WebView + nodejs-mobile – Hub runs in-process in the app
apps/server             Node + WebSocket – hosted Web build (the only variant that needs a server)
packages/core           model, Connector/ProviderFactory contract, Hub, Mesh-Groups
packages/store-sqlite   SQLite Store (accounts, mesh groups, jobs)
packages/host            createHub(): the single list of shipped providers; shells contain no logic
packages/provider-*     one package per messenger (whatsapp = Baileys, signal = stub)
```
Every host just calls `hub.call(method, params)` and `hub.subscribe(...)`; the UI's `api.ts`
picks the transport (Electron IPC / Android bridge / WebSocket).

## Adding a messenger
Create `packages/provider-<name>` default-exporting a `ProviderFactory` (see `packages/core/src/provider.ts`),
then add it to `packages/host/src/index.ts` – all shells pick it up.
Providers deal in *native* ids only; the Hub namespaces them as `<accountId>:<native>`.
Providers in other languages (e.g. a Go/whatsmeow or Rust/libsignal binary) can be wrapped as a
`Connector` that talks JSON over stdio – desktop/web only, awkward on Android.

## Platform notes
- **Web:** WhatsApp/Signal need a long-lived client session, so the web build talks to a Node server you host. Needs auth + TLS (none yet).
- **Android:** Node can't run in a plain WebView; use nodejs-mobile (via a Capacitor plugin). Background execution limits will need a foreground service.
- **Security:** keys and plaintext live in the Hub process. Electron: contextIsolation + sandbox are on; store account data encrypted (TODO, e.g. OS keychain via `safeStorage`).

## Providers
- **WhatsApp:** Baileys – unofficial, can break or get accounts banned. Alternatives later: whatsmeow as stdio sidecar.
- **Signal:** `@signalapp/libsignal-client` only gives crypto primitives; linking, websocket service, prekeys, groups v2 still have to be built (stub now).

## Mesh-Groups (`packages/core/src/mesh.ts`)
Virtual group living only in your core. Members are 1:1 chats on any platform; your accounts relay each message to the others
as `[Group · Alice] text` (receivers see your account as sender). Loop guard: own sends are never re-ingested; duplicates dropped.
Caveats: relay sees plaintext (your device), only works while the core runs, automated relaying risks bans.

## Backend runtime (embedded or standalone)
`startBackend(dataDir)` (packages/host) builds the Hub with SQLite and calls `hub.init()`, which restores accounts,
mesh groups and pending jobs and starts the scheduler – no UI required. Electron and Android run it in-process;
`apps/server` runs the very same thing standalone. The `Scheduler` (core) is a durable job queue with retry/backoff;
mesh relays and `scheduleMessage` are jobs. Jobs only run while the host process is alive (desktop: needs tray/background mode;
Android: foreground service; guaranteed 24/7 only on the standalone server).


## Message archive, accounts and read-only history (Hub)
- **Archive:** the Hub stores every message it sees (live events, history pages the provider returns, own sends) in SQLite,
  merged on write so a history replay never undoes edits, deletions, reactions or delivery progress. History reads come from
  the archive and are topped up from the provider when it can know more. Providers keep only their own session state.
- **Encryption at rest:** payload columns (messages, chat lists, aliases, mesh groups, account labels) and the media cache are
  AES-256-GCM sealed. Ids and timestamps stay plain (ordering/retention). Key: `UNIMSG_DB_KEY`, or the OS keychain on desktop
  (Electron `safeStorage`), or a 0600 key file. A key file next to the database protects against copying the database alone.
- **Account lifecycle:** *Sign out* logs the provider out but keeps the archive: chats become read-only (`Chat.offline`),
  with timeline markers (signed out / unlinked / signed in again, "messages in between may be missing"). *Sign in again*
  relinks the same account into the same archive. *Remove* deletes the account and everything stored for it.
  A phone-side unlink is detected (`needs-login` after being linked) and treated the same way.
- **Retention:** optional automatic deletion of messages and cached media older than N days (Settings → Privacy).
- **Media:** attachment bytes that were opened are cached (encrypted) so they survive sign-out; unopened ones are not available offline.

## Merged chats (local-only)
The same person often has 1:1 chats on several accounts/apps. `mergeChats({chatIds, name?})` shows them as ONE chat with one timeline.
It is Hub-level state (table `chat_merges`, like aliases and mesh groups): nothing is sent to any network and no message is copied.
- **Ids:** a merge is `merge:<uuid>`. Messages keep their real `chatId` (`<account>:<native>`), so attachments, react, edit, delete, vote,
  forward, markRead and replies route to the owning provider unchanged. The merge id is only a *view key*: history/search rows and the
  events `message`, `message-update`, `receipt`, `typing`, `history-updated` of a member chat additionally carry `mergeId`. It is never stored.
- **RPC:** `mergeChats` (ids of existing merges may be passed to extend/combine), `unmergeChat`, `addMergeMember`, `removeMergeMember`
  (below two members it dissolves), `setMergePrimary`, `setMergeVia` (remembered "send via" member), `merges`, `mergeSuggestions({chatId})`
  (same name / phone / handle). Calls addressed to a merge id are rewritten to the owning member (by `messageId`, or `via` / saved choice /
  member of the newest message for sends, scheduled sends, forward targets and typing). `markRead` fans out to every member.
- **Rules:** only DMs (no groups, channels, mesh groups); a chat is in at most one merge; signed-out archives can be members. Removing an
  account drops its chats from the merge; the merge lives on with what is left (and goes when nothing is).
- **Snapshot:** member chats get `mergedInto`; a synthetic row (`provider: "merged"`, `mergeMembers`, `mergeSendVia`, `mergeLastVia`) carries
  name (alias > merge name > primary's name), the primary's avatar, summed unread, newest preview/time and the pin/mute/archive flags
  (flags and aliases of a merge are stored under its id).
- **Timeline:** `history(mergeId, {limit, beforeMessageId, beforeChatId})` interleaves the members' archives by (time, id, chat), pages by
  the anchor message, tops each live member up from its provider like a normal chat (background when the archive has content) and adds the
  accounts' link markers prefixed with the account label.

## Local security
The WebSocket server only accepts browser connections from localhost origins by default (stops any website from talking to
your local backend), supports `UNIMSG_TOKEN`, and refuses to bind a non-loopback address without a token. Put TLS in front of a
hosted deployment.

## Provider contract highlights
Capabilities gate every optional feature (reactions, edits, deletes, polls, locations, contact cards, group management,
communities, avatars, own profile + privacy, contact sync). Providers return native ids; the Hub namespaces them.
Names a user gives people/chats (aliases) and pin/mute/archive flags live in the Hub store; they never go to the network.

## Folders (local-only)
The communities in the left rail behave like folders. `moveChat({chatId, folderId})` stores a per-chat override (table `chat_folder`; `"personal"`, a
community id or a user-folder id; `null` resets) and never touches the network or any message. User folders (`createFolder/updateFolder/deleteFolder`,
table `folders`, ids `folder:<uuid>`, shown as `Space{local:true, color, icon}`) sit beside network communities; `setRailOrder({ids})` orders both
(setting `railOrder`). Deleting a folder drops the overrides pointing to it, so its chats return to their original place. `packages/core/src/folders.ts`
(`applyFolders`, shared with the UI mock) turns raw spaces/chats into the snapshot: `Chat.spaceId` = effective folder, `networkSpaceId` = the network's own,
`folderId` = the override. A network community whose effective membership is ONE chat gets `Space.collapsed` (no rail entry) and its chat
`collapsedFrom` and is listed under Personal (setting `collapseSingleChatCommunities`, default on; a muted community keeps its chat muted, archive does not
follow). User folders never collapse. Merged chats move as one row (a member id is redirected to its merge id).

## Interactive verification (Matrix emoji / SAS; generic)
`Capabilities.verification` + event `verification` ({accountId, id, phase `incoming|waiting|sas|confirming|done|cancelled`, incoming, other {kind device|user, name}, emoji [emoji,name][], reason}) + optional connector methods `verificationStart/Action/Status/Setup/Recover`. The Hub adds the account id to the event, remembers open verifications for `pendingVerifications` (a UI that connects later still sees them), and routes the five calls (chat ids made native, 30 s / 120 s timeouts); it forwards nothing to proxy accounts (`provider-remote` drops the events). The UI (`apps/ui/src/VerifyDialog.tsx`) is provider-independent: `<VerifyHost/>` shows the incoming-request toast (+ browser notification when notifications are on), the emoji dialog, the set-up dialog (password -> recovery key shown once, never stored) and the recovery-key dialog; `AccountVerify` (account card) and `PersonVerify` (contact panel) are the entry points. Matrix implements it in `packages/provider-matrix/src/verification.ts` (details in that README); status: fake-verified only (fake SDK objects, mock UI hooks `__mockMatrixVerify` / `__mockMatrixAuto` / `__mockVerifyLog`), never run against a real homeserver.

## Contract additions (categories, counts, cards, per-account capabilities, mentions, requests, provisional chats)
- **`Chat.category`** groups chats inside a community (collapsible headings in the UI, collapsed state kept in localStorage; chats without one stay on top). `Chat.canManage: false` hides member/rename/picture controls for one chat although the account may manage others (Discord server channel vs group DM).
- **Exact counts:** `Reaction.count?`, `Poll.options[].count?` (total when `senderIds`/`voters` are incomplete; UI shows `count ?? length`, the reactors list adds "and N others"). Never pad ids with fakes.
- **Cards:** `Message.cards?: Card[]` (`Message.card` = legacy `cards[0]`; use `cardsOf(m)`), `Card.image?: {attachmentId, width?, height?, thumbnailDataUrl?, layout?}`. The image is fetched with the ordinary `attachment` call (`Connector.downloadAttachment` must resolve that id; it need not appear in `Message.attachments`), so the UI never hot-links remote hosts.
- **Per-account capabilities:** `Connector.capabilities` may be a getter. The Hub reads it live (start, every account event, `accounts`/`snapshot`) and publishes `Account.capabilities` (also in `account` events and `snapshot.accounts`). The UI resolves capabilities through the chat's account (`capsOf`), falling back to `ProviderInfo.capabilities` (e.g. signed-out archives). New flags: `mentions`, `requests`, `pollVote`.
- **Mentions:** `OutgoingMessage.mentions?: {id, name, start, length}[]` (UTF-16 offsets of the `@Name` span; the Hub drops malformed/overlapping ones). The composer autocompletes members (cached per chat) in groups/channels when `caps.mentions`.
- **Login:** `LoginField.type "checkbox"` (+`required`, value `"true"`/`"false"`), `LoginPrompt.warning {text, severity}` rendered as a styled box; the UI refuses to submit unchecked required fields.
- **Requests:** `Chat.request`, `Connector.acceptRequest/declineRequest` (RPC of the same name, capability `requests`). `Chat.unreadApprox` = unread is only 0/1 (dot instead of number).
- **Provisional chats:** `startChat` may return `provisional: true`; the Hub lists it (memory only) until the first `send()` returns a message with a different `chatId`, then emits `chat-resolved {from,to}` (before the `message` event) and the UI re-keys the conversation.

## Backup / migration
Code: `packages/core/src/container.ts` (file format), `backup.ts` (what goes in, merge rules, RPCs), `chatexport.ts`, Store methods
`exportRecords / countRecords / inTransaction`, `apps/server/src/backup-http.ts`, UI `apps/ui/src/BackupPanel.tsx` (Settings > Data).

**File `*.unimsg-backup`** (extension kept from the old name): `"UNIMSGBK" | u16 version(1) | u32 headerLen | header JSON | frames`.
Header (plain, authenticated): scrypt params (N default 2^16, r=8, p=1, salt), cipher aes-256-gcm, compression (gzip default; zstd when
the writing Node has it; gzip is the portable choice for phones), chunk size, nonce prefix, and an HMAC "key check" so a wrong passphrase
is distinguished from damage. Frames are 64 KiB AES-256-GCM chunks, nonce = prefix || u64 counter, AAD = sha256(preamble) || flags || counter;
the last frame (flag 1) is a footer with sha256 + length of the plaintext, entry counts and the manifest hash. Truncation, reordering,
dropped/duplicated frames, trailing bytes, bit flips and unknown versions are all rejected with a user-facing `BackupError`; the writer writes
`<file>.part` and renames, so a failed/cancelled export leaves nothing. Plaintext = gzip(entries), entry = `u32 headLen | head JSON {kind,size,...} | body`.
Entries in order: `manifest` (counts, source app version/name, created time, parts, account list), `session` files, `media` blobs, `rows` (NDJSON StateRecords).
Everything is streamed; memory is a few chunks plus one media/session file.

**Content.** (a) Messages and settings: decrypted rows from `Store.exportRecords()` (accounts, messages, chat cache, aliases, chat flags, folders,
chat->folder, merges, mesh groups, settings, account events, jobs); the source data key is never needed or shipped; the importer re-seals with the target key.
(b) Media cache: attachments that were opened, decrypted into the archive and re-sealed on import (cache key = chat|message|attachment, rewritten when the account id is remapped).
(c) Sessions (off by default): the account directory files minus an allow/deny list (no `*.tmp/.lock/.log`, no cache/avatars/media/tmp dirs, no symlinks, <=128 MB each),
copied generically. Key files that live in the account dir (`discord-session.key`, `teams-session.key`, `threema.key`, `signal-store.key`) travel with their sealed file; Mattermost, Instagram, WhatsApp and Matrix keep plain 0600 files.
Secrets sealed by a key OUTSIDE the account dir are made portable by the optional `ProviderFactory.exportSession(dir)` / `importSession(dir)` hooks (provider.ts): export adds a portable file and omits the unportable sealed one, import re-seals for the target.
Implemented for Discord (`UNIMSG_DISCORD_KEY`). Still not portable in that situation: Teams/Threema with `UNIMSG_TEAMS_KEY` / `UNIMSG_THREEMA_KEY` and Signal with an external `KeyProvider` (none is wired in host/desktop today, so Signal currently always uses `signal-store.key`); each needs the same ~15 line hook in its package.

**Import.** `importInspect` (header + manifest + account plan, checks the passphrase), `importData({path|uploadId, passphrase, mode})`.
Pass 1 authenticates the whole archive (nothing written). Pass 2 stages session/media files in `<backups>/.import-*`, then applies all rows in ONE store transaction
that also covers the footer check (rollback on any error, cancel or tampering), then moves staged files into place (never overwriting), then `Hub.reloadFromStore()`.
`new-install` needs an empty target. `merge`: messages by id, existing copies are never changed (only missing fields are filled), aliases/flags/folders/merges/settings only where absent,
accounts matched by id+provider, else provider+label (chat ids are remapped), otherwise added. Every account that is not matched arrives as an **archived read-only account**
(the normal "signed out, Sign in again" state, with a signed-out marker in its timeline). With sessions, session files are restored but the account still stays stopped and is listed by `movedAccounts`
("moved from another install; the source must be signed out/stopped"); `confirmMovedAccount` starts it, `dismissMovedAccount` discards the session. Pending scheduled jobs are only imported for accounts that arrive with a session.

**One-account transfer (device to device; UI: Settings > Data > "Move a login to another device", `MoveLogin.tsx`).** Source: `exportData({accountIds:[id], parts:{data:false, sessions:true}, passphrase})` makes a small session-only
archive (account record + that account's session files; add `data:true` to carry its history too). Target: `importData` in `merge` mode; if the account already exists there as an archived account
(e.g. the phone had it signed out) its session is adopted, otherwise it is added. Then on the target `confirmMovedAccount` starts it. Source, once the user confirmed the file is saved:
`moveAwayAccount({accountId, confirmedSaved:true})` stops the connector WITHOUT remote logout (the session now lives elsewhere), wipes the local session directory, marks it archived
(`backup.movedAway` setting) and keeps the chat archive read-only. Do the target's confirm only after the source moved away: two live copies of a linked-device session break WhatsApp/Signal.

**RPCs** (Hub.call): `exportEstimate`, `exportData` (+ events `backup-progress {op, stage, done, total}`), `backupCancel`, `importInspect`, `importData`, `movedAccounts`,
`confirmMovedAccount`, `dismissMovedAccount`, `moveAwayAccount`, `exportChat({chat, format:"html"|"json", from?, to?})` (self-contained HTML with cached images inlined, merged chats too),
and for transports without HTTP `backupUploadStart/Chunk/End`, `backupDownloadChunk`, `backupDiscard`.

**Transport.** Paths are governed by `BackupPolicy` (`HubOptions.backup`, `BackendOptions.backup`): `"any"` (desktop: path comes from a native dialog; the Electron main process only lets exportData/importInspect/importData name paths the user picked in `showSaveDialog`/`showOpenDialog`, see `apps/desktop/src/dialogs.ts`), `"dir"` (default: only inside `<data>/backups`),
`"none"`. `apps/server` uses `"dir"` on loopback and `"none"` otherwise (`UNIMSG_BACKUP_DIR`, `UNIMSG_BACKUP_MAX_BYTES`, default 16 GiB) and serves, on the same port and with the same token/origin rules as the websocket,
`POST /backup/upload` (raw body, size counted while streaming, answers `{id}` for `importData({uploadId})`) and `GET /backup/download/<id>` (one-time 192-bit id from `exportData({deliver:"download"})`, 15 min, file deleted after a completed download).
The Electron/Android UI uses the chunked RPCs (4 MiB pieces over IPC) and `showSaveFilePicker` when present. Desktop agent TODO: pass `backup: {paths:"any"}` to `startBackend`, add `dialog.showSaveDialog/showOpenDialog` IPC and then call `exportData({targetPath})` / `importData({path})` instead of the chunk path (faster for GBs).

## Global search, mark-all-read, download-all-media (Hub)
Code: `packages/core/src/{search,search-store,readjob,mediajob,hub-extras}.ts`; the Hub only wires them in.
- **`searchAll({query, limit, before?, accountIds?, providers?, kinds?, since?, until?, deep?})`**: payloads are sealed, so SQLite cannot search them
  (and FTS5 over plaintext would defeat the encryption). The Hub keeps an in-memory index of lower-cased `messageSearchText` per message, streamed from
  `Store.scanMessages` (primary-key keyset pages, yielding to the event loop) at startup and kept current by a store wrapper (`withSearchIndex`) on every
  write, edit, deletion, retention purge and account removal; a backup import rebuilds it. **Bounded**: 500k messages / 48M chars / 1000 chars per message
  (`HubOptions.search`); when full the oldest messages leave the index (`index.truncated`, `coveredFrom`), `deep: true` then scans the sealed archive for
  the older part (slow, time-boxed). Results: every term must match (AND), ranked by phrase / whole-word / recency, grouped by chat (merged chats resolve to
  their merge row), with snippet + highlight ranges + message ids; `before` is the `next` cursor of the previous page. Signed-out archives are included
  (`offline`).
- **`markChatRead({chatId, sendReceipts})` / `markAllRead({scope, sendReceipts, wait?})`**: `scope` = `all`, `personal`, an account id or a community/folder id.
  Calls `Connector.markRead` with the newest incoming message id of every affected chat (merged chats: every member), at most ~3 provider calls per second,
  as a job with `mark-read-progress` events (final event: `failures`, `cleared` = rows whose counter may be cleared). Providers that send receipts
  (`readReceipts`) are skipped when the user's "send read receipts" setting is off; `markRead`-only providers (Mattermost, Discord) are always called.
  Per chat: `ok`, `local` (no support / receipts off / signed out / nothing stored: counter cleared in the UI only) or `failed` (counter kept). `chat-read` events
  let other windows clear their counters. `cancelMarkRead`.
- **`estimateMedia`, `downloadAllMedia({accountId, chatIds?, maxBytes?})`, `cancelMediaDownload`, `archiveMedia`**: walks the archive's attachment descriptors (and card
  images) of one account, downloads what the sealed media cache lacks through `Connector.downloadAttachment` (2 workers, paced, per-file timeout), emits
  `media-progress`, is cancelable and resumable (a new run skips cached files). `archiveMedia` tells a read-only archive which chats have media that is "not
  available offline". Sign-out / removal cancels a running job.
- A message that becomes `deleted` loses `card/cards/attachments/poll/location/contacts` in the archive; `OutgoingAttachment` carries optional `width/height/gif/caption`.

## Pinned messages
`Capabilities.pinMessages` (+ `pinDurations` in seconds, 0 = until removed, for networks with expiring pins) gates the feature. `Message.pinned/pinnedAt/pinnedBy/pinnedUntil` live in the archive. A connector implements `pin(chatId, messageId, pinned, {durationSec})` and optionally `pins(chatId)`, and reports pins made elsewhere (other people, own other devices) as `message-update` patches `{pinned,...}`. Hub: `pin` routes like react/edit (a merged chat resolves the owning member chat), checks the capability, validates the duration (default 7 days) and patches the archive itself; `pins {chatId}` unions the members of a merged chat, newest pin first, drops expired/deleted pins, and when the connector can list pins its answer is authoritative for the archive flags. Sync: the pin fields are their own last-writer-wins register per message (`MsgRec.p`, stamp `p` in the ledger meta), separate from content, so an edit never undoes a pin and the later pin/unpin wins. UI: `Pins.tsx` (bar under the header, list in the info panel, menu item with duration choice in `Conversation.tsx`).

## Per-recipient receipts ("Message info")
`Message.receipts?: {id, delivered?, read?}[]` (ISO times, `id` in the sender-id space) on MY messages. Providers emit the `receipt` event
with `by` (sender id) + `at` (time) for one recipient (`status` "delivered" or "read"; read implies delivered); without `by` it stays the aggregate
status. The Hub merges per id (a field is never dropped, a time never moves backwards, history replays never lose receipts), stores them sealed
with the message and sends the merged list as a `message-update` patch `{receipts}`. `Capabilities.receiptDetails` says the network reports this per
member (WhatsApp, Signal, Matrix: read only, Instagram: read only); the UI makes the ticks a "Message info" button for those accounts and for every
1:1 chat (single recipient, or the aggregate state with a note when nothing more is known).

## Rail groups and multi-select (UI features, local only)
- **Rail groups** (`packages/core/src/railgroups.ts`, UI: `apps/ui/src/{RailGroups.tsx,railGroupOps.ts}`): dropping a rail icon (community or folder) on the middle of another creates a named, coloured group
  (Discord-style folder). Stored as the Hub setting `railGroups` = `[{id:"group:<uuid>",name,color?,members:[spaceIds]}]`; RPCs `railGroups` (cleaned against the spaces that exist now) and `setRailGroups` (strict validation, emits `spaces-changed`).
  A group sits where its first member sits in the existing `railOrder` (members are kept adjacent); Personal and groups themselves can't be members. Settings travel with backups / future sync like any other setting.
- **Chat multi-select**: shift+click range, ctrl/cmd+click toggle in the chat list; bulk actions call the existing per-chat RPCs (`moveChat`, `setChatFlags`, `markChatRead`) one by one with a progress notice and a failure summary (UI-side only, no new RPC).
- **User categories** (`packages/core/src/categories.ts`, UI: `apps/ui/src/Categories.tsx` + the list in `App.tsx`): the user's own headings INSIDE a view (a community, a user folder or `personal`), local only.
  Stored as the Hub settings `userCategories` = `{ [view]: [{id:"cat:<uuid>", name (<=40, unique per view, case-insensitive), color?, order}] }` and `chatCategories` = `{ [chatId]: "cat:<uuid>" | "none" }`
  (absent = follow the provider's `Chat.category`; `none` = explicitly uncategorised, hides the provider's). Settings, so backups / future sync carry them (a `merge` import only fills settings that are absent).
  RPCs: `categories`, `createCategory({spaceId,name,color?})`, `updateCategory({id,name?,color?|null})`, `deleteCategory({id})` (chats fall back to their provider category), `setChatCategory({chatIds,categoryId|null|"none"})` (batch, atomic; the category must belong to the chats' current view),
  `setCategoryOrder({spaceId,ids})`. Snapshot: `Chat.category` = EFFECTIVE name (user category, else the provider's while inside a community/folder; Personal has no provider headings), `Chat.categoryId` = user category, `Chat.providerCategory` = original, and `categories: {[view]: UserCategory[]}` (so empty ones show).
  An override only holds while its category belongs to the chat's current view: `moveChat` / `deleteFolder` call `reconcile()`, which clears mismatched overrides (and `none`) of moved chats and drops categories of deleted folders (network communities' categories are kept, they may just be offline; chats unknown right now keep their override).
  List order: uncategorised chats on top, then the user's categories in their order (empty ones too, "Drop chats here"), then the provider's categories in provider order. UI: header button / space menu "New category…", heading menu (Rename, Colour, Collapse/Expand, Mark category as read, Move up/down, Delete), chat / bulk menu "Move to category…", drag chats onto a heading or a row, drag headings to reorder.

## Device sync (packages/sync, packages/provider-remote, apps/server relay)
Keeps several installs of one user in step with **no server we operate**. Code: `packages/sync/src` (`service.ts` orchestrates), UI `apps/ui/src/SyncPanel.tsx` (Settings > Sync devices), optional relay `apps/server/src/relay.ts`.
Everything runs in the Hub's process; `Hub.attachSync` gives the service a `SyncHostApi` (events, reload, connector access, media cache, provider hooks) and routes the `sync*` RPCs.

**Data model.** `SyncStore` wraps any `Store` (**decision: no Store change-feed**: a wrapper sees every write that goes through the Hub, needs no change in MemoryStore/SqliteStore and is a pure pass-through until a group exists; replication writes bypass it, so nothing is echoed).
Each synced entity (message, alias, flags, folder, merge, setting, account, chat cache, credentials stub) has a row in `sync.db` (`ledger.ts`: key, local seq, HLC stamp, merge metadata, who delivered it; **no content**). Peers remember "applied your ledger up to seq N" (cursor per peer + ledger id), so replication is resumable and idempotent.
Merge rules (`crdt.ts`, all joins commutative/associative/idempotent, randomised tests): registers = LWW on the HLC stamp (device id tie-break, tombstones are registers); messages = content (edit wins by `editedAt`, then stamp), sticky delete, status only moves forward, and **reactions = add/remove set per (emoji, sender)** (LWW-element-set: each element has its own stamp, removal is a tombstone; concurrent reactions of two devices both survive). A merge that holds more than the sender had is sent back (no echo suppression for it).
**Chat cache vs live connector:** a device with ANY connector for the account (own login or proxy) ignores a peer's cached chat list for it (it asks the network itself); accounts that are not live here take the cache (read-only archive view).

**Initial transfer (snapshot).** If the peer's cursor on our ledger is 0 (or >20k entries behind) and we have >= 800 entities (>= 50 when the peer reported an empty store), the sender writes the current state of the ledger as ONE archive in the backup container (`core/container.ts`: AES-GCM frames, gzip, authenticated footer) keyed by `HKDF(group key, snapshot id)` instead of a passphrase, and offers it (`snap-offer {id,size,sha,cursor,tag}`). The receiver stores the ENCRYPTED bytes as they arrive (`snapshots/in-*.part`, offset persisted every MiB), answers `snap-go {from}` so an interrupted transfer **resumes at the byte where it stopped** (the sender keeps the file for an hour), verifies sha-256, applies the entries through the normal join in batches, sets the cursor to the snapshot's, acknowledges, and incremental ledger sync continues from there. Credentials never ride in a snapshot (re-sent afterwards, still needing confirmation). The empty target skips echo-back of what it just received. Progress: `sync-progress {phase:"snapshot", snapDone, snapTotal, snapDir}`.

**Transfer order (priority classes, #65).** The sender serves the ledger in classes, each with its own cursor, so the accounts show up before the long transfer: (1) `g` = all non-message rows (accounts, credentials, settings, folders, chat folders, merges, mesh groups, flags, aliases, chat caches), always drained first and again whenever a new one appears; (2) a "head" of the 600 newest messages by time (`cls:"h"`, advances no cursor, a fresh peer only; the later ordinary pass re-sends them and the receiver skips them by merge); (3) `m` = the message backlog in ledger order, resumable by its cursor; (4) files, which only start when the want list is pumped (`pumpMedia`), never inside the ledger stream. A snapshot (big first transfer) is offered only after class `g` is through. `have` carries both cursors (`cursor` = messages, `g`); batches carry `cls`, the receiver advances only the matching cursor and persists `{applied, g}` per peer. A peer that reports no `g` (older version) gets the old single-cursor stream, and a batch without `cls` advances both. The ledger has an indexed class column (`m`). Receiver: an account batch triggers an immediate `host.reload` (event `accounts-changed`), message batches reload at most every 1.5 s. Progress carries `accts {done,total}` and `chats {done,total}` (batches carry `tot`, `sg`, `sm`) next to the media counters, shown as phases in Sync devices.

**Media blobs** (`blobs.ts`). Messages carry attachment metadata, not bytes. Replicated messages put missing attachments on a want list. Bytes move by **content hash**: `blob.q {chat,msg,att}` -> `{hash,size,mime,name}`; a local copy with the same hash is reused (dedup), otherwise 192 KiB ranges via `blob.get`; ranges are kept **sealed on disk** (AES-GCM, this device's key) so a transfer resumes; SHA-256 is verified before the bytes enter the Hub's media cache (sealed with the data key). On demand: `Hub "attachment"` falls back to `SyncHandler.fetchMedia` when the account is signed out / the network download fails. Background (per-device policy `off | wifi | all`, max file MB, max total MB; "wifi" = not metered: `syncSetMetered`, set from `navigator.connection` by SyncPanel or by the Android shell). Never for accounts with sync mode `none` (neither requested nor served). `sync.db` stores sha-256 hashes of cached media (no content).

**Big credential sessions.** Mattermost/Discord/Teams logins (mode "History and login"): small ones inline, larger ones as a stub; the receiver pulls the files with `rpc cred.get` in pieces (`bulk.ts`, 120k-char pieces, reassembly caps). Limits (`LIMITS`): 64 MB total, 512 files; beyond that the account shows a clear error. Received sessions are **staged sealed** until the user confirms; Discord (and any provider with `exportSession/importSession`) is exported portable and re-sealed on the receiver (no shared `UNIMSG_DISCORD_KEY` needed).

**Pairing (security).** Code (16 letters, scrypt psk) + Noise_XXpsk0. After the handshake **both** devices show a 6-digit short authentication string (HMAC of the Noise transcript; `sasOf`); the inviting device shows "Device X wants to join" and nothing (not even the group key) is sent until the user confirmed on the inviter AND on the joiner (`syncApproveJoin`, `syncConfirmJoin`). Wrong codes are counted **per source address** (3 tries, then lockout 30 s, 1 min, 2 min ... up to 1 h); the pairing session stays open for others (a LAN attacker can no longer burn the attempts); 20 wrong tries over all sources close it; limits on half-open connections per address and global; key/ID comparisons are constant-time. One code admits one device; a denial rotates nothing but locks the source.

**Pairing works from either side, with nothing to configure (2026-11-14).** Problem it solves: a typical Linux laptop has a default-drop firewall, so inbound TCP (and multicast / mDNS) is dropped while its outbound connections work, and a phone has no inbound firewall. Rules:
- The device that **enters** the code (or scans the QR) **dials out**; the device that **shows** it **listens**. Which device is "the old one" does not matter: the code only has to be shown where it can be reached. Roles in the group are decided after the handshake, by what each side holds (`hello.grp` = live members): the side with a multi-device group hosts (admits the new device) even when it was the one that dialed; otherwise the side that showed the code hosts. Two devices that both already have groups refuse each other with a clear message. A solo group (created just by showing a code) is silently replaced when that device ends up joining.
- **Well-known port** 45045 (fallback range 45045-45052, `discover.ts`): the persisted port is tried first, then the range, a random port only as a last resort. `SyncOptions.wellKnown` overrides the range (tests).
- **Candidates**, all tried in parallel by `dialAny` (concurrency 64, short timeouts, first authenticated handshake wins, every other attempt gets the abort signal and a late winner is closed): addresses in the QR link, a typed address (then nothing else is scanned), hints (addresses of the last 4 successful pairings, kv `pairHints`), addresses of known group members, mDNS (`m=pair` services; the browser is started for the duration of the join), and a **LAN probe**: for each IPv4 interface that is private (RFC 1918 only), not internal, not VPN / container / cellular by name (tun, tap, wg, tailscale, docker, br-, veth, virbr, rmnet, ccmni, ...), not CGNAT / link-local / public, the other hosts of its subnet (never wider than a /24, at most 512 hosts in total, nearest first, never ourselves) on 45045..45052; connect timeout 400 ms; a host that drops packets is tried once, a host that answers RST is walked through the ports of the range. Public or cellular-only machines probe nothing. Nothing is scanned outside tests' fakes (`SyncOptions.net` injects interfaces and a connector; with `bindHost` and no injected interfaces the probe is off).
- **Authentication of whatever answers** is the existing Noise XXpsk0 handshake keyed by `scrypt(code)`: the code is never sent, our static key is only revealed after the other side proved it knows the code, and a host that does not know it just closes (a failure at an explicitly named / announced host ends the attempt at once as "code not accepted"; a failure at a probed host is only counted, the scan continues; a UniChat that is not pairing rejects softly and is not counted against us). Failed attempts are rate limited per source address exactly as before (3, then lockout 30 s, 1 min, ...).
- **Role flip.** If every candidate is unreachable (`joining.reason = "unreachable"`), the UI says that this device could not reach the other one and offers "Show a code here instead": it starts pairing here, and on the other device the user types this code, which dials in the working direction. If the user starts on the reachable side first, the other side's "type a code" finds it with the probe, no flip needed. A wrong code (`reason = "code"`) asks to check the letters and does not offer the flip. `approval.direction` / `joining.direction` (`incoming` | `outgoing`) tell the UI which way the connection was made ("The other device connected to this one" / "This device connected to the other one").
- After pairing, normal sync is dialing as before (known addresses, mDNS, relays). The side that was dialed keeps its listener on if the user left "let the other device find this one later too" ticked (default), so a blocked laptop keeps working by dialing out to the phone. Relays stay optional and off; no third-party service is involved.
- RPC: `syncJoin {code, host?, port?, link?, deviceName?, keepListening?}` -> `{sas, hostName, role: "joiner"|"host", via}`; `syncStatus.joining = {state, reason?, error?, direction?}`, `solo`, `joinBusy`.

**Simplified sync UI and nearby pairing (2026-11-14).** Settings > Sync devices is now: "Your devices" (name, online dot, last synced, Rename for this device, Remove), ONE button "Add a device" (creates the session at once: the group is created silently, the name defaults to the device name, `keepListening` is on; QR + code + Copy link + "Waiting for the other device..."), a small "Connect to another device" (Nearby devices with one-tap Connect, Scan QR code, type a code or paste a link) and a closed "Advanced" section (rename/pause/stop, per-account sharing, network, addresses, relay, media, connect-by-address). One confirmation dialog on both devices: big 6-digit number, "It matches" / "Cancel" ("Allow <name>?" for nearby, "Add <name>?" for a code, "Connect to <name>?" on the joining side); it closes by itself and a toast says "Synced with <name>" once the first sync is idle; the first sync shows one progress bar with counts. After pairing, `tick()` re-dials known addresses / mDNS every 10 s with back-off; the UI only says "Couldn't reach <name>. Make sure both are on the same Wi-Fi." Session secrets are still NOT shared by default (per-account "History and login" lives in Advanced and keeps its confirm dialogs).
- **Nearby (no code), `nearby.ts`.** Any device showing "Add a device" is in `pairing` state and announces `m=pair, nb=1` over mDNS (`nb=0` once its prompt budget is spent); the join side calls `syncBrowse` (browses mDNS for 45 s per call, UI repeats every 20 s) and lists `status.discovered[].nearby`; `syncJoinNearby {host, port}` dials ONE address with prologue mode `nearby`. That handshake is Noise XXpsk0 with a PUBLIC psk, i.e. an encrypted but UNAUTHENTICATED channel; the only authentication is the 6-digit number both people confirm (like Bluetooth numeric comparison). Because an attacker who may pick its keys after seeing the other leg could grind 10^6 keys until both legs show the same digits, the number is not derived from the Noise transcript alone: after Noise the host sends `commit = SHA256(label|T|Nh)`, the joiner sends `Nj`, the host reveals `Nh` (joiner verifies the commitment), and both use `T' = HMAC(T, label|Nh|Nj)` for `sasOf`. A man in the middle must fix its nonce on each leg before it learns the other's, so the two numbers collide with probability 10^-6 per attempt (tested: relaying attacker over real sockets shows different numbers; revealing another nonce aborts). Both users must still approve (`hostOk && joinerOk`; never auto-confirmed), and nothing (group key, device list) is sent before. Once the numbers are confirmed the result equals the code path (static keys authenticated by the SAS); the code path is stronger before confirmation (~50 bit code).
- **Limits.** Nearby only while "Add a device" is open; at most `maxNearbyPrompts` (5) prompts per session (counted when the attempt starts, aborted ones too), then mDNS says `nb=0` and `nearby` is refused; handshakes that die after the public psk count against the source address (`srcFail`, escalating lock-out, 3 per source); a host that denies a prompt locks that source out; one pending prompt at a time (`busy`); a cancelled/denied attempt stores nothing (no group on the joiner, no `pairHints`, host's device list unchanged). Role rules (group holder hosts) are unchanged.
- **Deep link.** The QR encodes `unichat-sync://pair?h=&p=&c=&k=`. Android: `MainActivity` has a VIEW/BROWSABLE intent filter for scheme `unichat-sync`, host `pair` (launchMode singleTask: `onNewIntent`), forwards the link through `NodeBridge.openSyncLink` (shape + length checked, held until a page is attached) as `{ctl:"sync-link"}` -> `shim.js` sets `window.__unimsgSyncLink` and fires `unimsg-sync-link`. The UI (`syncLink.ts`, App, Panels, SyncPanel) opens Sync devices and calls `syncJoin {link}` by itself; only the number comparison is left. The web UI accepts `?pair=<link>`; the code field accepts a pasted link; "Scan QR code" uses getUserMedia + bundled jsQR 1.4.0 (loaded only when the camera opens; falls back to a message without camera). A hostile link can only make this device dial an address and offer a handshake; the code and key pin in the link and the number comparison still decide.
- RPC: `syncJoinNearby {host, port, deviceName?}` -> as `syncJoin`; `syncBrowse` -> `{available}`; `status.approval.nearby`, `status.joining.nearby`, `status.discovered[].nearby`.

**Listener / exposure.** The sync listener is **closed by default**. It opens while a pairing code is shown (scope: local network) or when the user turns on "Sync over the network" (persisted `listen` setting: scope `loopback` | `lan` (one socket per private IPv4 address; never public or CGNAT/VPN addresses implicitly) | `address` (one specific local address, e.g. Tailscale `100.x`; `0.0.0.0` is refused)). Only devices that pass the Noise handshake with the current group key AND whose static key is a non-revoked member get a session; everything else is dropped; per-IP connection rate and failure lockout apply. A device with its listener off still connects *out* to the others (dial-only, e.g. a phone). mDNS announces only while a non-loopback listener is open (IPv4, SO_REUSEADDR, membership on each interface, send per interface; IPv6 not implemented; `status.discovery` says whether it works).

**Beyond the local network (no server of ours).** Every paired device has a LIST of addresses (`Addr`: tcp host/port incl. IPv6 and DDNS names, or relay URL; sources pairing / learned from the peer itself on every session / mDNS / manual), edited in the UI. Dialing races them happy-eyeballs style (best first by last-good, next ones 250 ms apart, relays only after 1.5 s), remembers the last good address, backs off exponentially per failed round. **NAT notes:** UDP hole punching is only available through the optional HyperDHT transport below (not the default); devices behind NAT work when (0) both turn on "Reach my devices from anywhere" (UDP hole punching through the public Holepunch DHT, or one you host), or (a) one of them is reachable (port forward / IPv6 global address / DDNS name / VPN such as Tailscale, WireGuard: use scope `address`), or (b) both use a relay. With IPv6 most home networks give every device a global address, only the router firewall needs a rule for the sync port.
**Reach my devices from anywhere (HyperDHT, 2026-11-14; `packages/sync/src/dht.ts`, Settings > Sync devices > Advanced > Network).** A fourth address kind, `{kind:"dht"}` (no host/port: derived), next to mDNS, saved tcp addresses and the relay. ON by default (user decision 2026-11-15; it only runs for a device that belongs to a paired group); no server of ours, no telemetry; nothing is loaded or opened unless the switch is on.
- **What it is:** `hyperdht` (the Holepunch DHT, pinned 6.35.0) gives a raw encrypted duplex stream to a public key, found by UDP hole punching through DHT nodes (no relay in the data path). EVERYTHING above it is unchanged: the same framing, the same Noise_XXpsk0 handshake with the group-key psk and the same member check (`checkRemote`) as over TCP. The DHT is never trusted for authentication; a stream that fails the handshake is closed like any other.
- **Identity.** Each device derives ONE keypair per group: `seed = HKDF-SHA256(ikm = device Noise private key, salt = SHA-256("unichat-sync-dht-group-v1\0" + group id), info = "unichat-sync-dht-identity-v1")`, `DHT.keyPair(seed)`. The Noise key is never used as a DHT key; the same device has an unrelated key in every group; nobody without the device private key can compute it. The public key is announced to the group through the group record (`Dev.dht`: filled in `mergeMembership` only when empty, replaced only by the device's own report in its `members` message, `keys` broadcast right after the node starts). The rotating group key is deliberately NOT an input (it changes on every revocation, which would silently change every device's address). Consequence: turn the switch on on each device while the devices can still see each other once (LAN or any other session) so the keys travel; a device that enables it later is found as soon as any session carries its record.
- **Server side.** A device with the switch on `listen`s on its derived key. The HyperDHT `firewall` only lets the DHT public keys of current, non-revoked members through, so a stranger cannot even open a stream (before any of our code runs); the Noise handshake + member check follow. Inbound DHT streams have no source address: per-source lockouts do not apply (the firewall does that job), the unauthenticated-session cap (8) does. Over the DHT only `mode: sync` is accepted: pairing and nearby are refused.
- **Dialing.** `candidates()` appends `{kind:"dht"}` for a peer whose `dht` key is known, when this device's node is running and its id is the LARGER of the pair (the smaller one only listens, like the relay rule; each side enabling it is required). `orderAddrs`: tcp (LAN, saved) first, then dht, then relay. `raceConnect` starts the DHT candidate only after `dhtDelay` (1.2 s) and cancels it when an earlier candidate wins, so a LAN success never opens a DHT stream; at most 2 DHT dials run at once (`DhtTransport.maxDials`), later ones queue and honour the abort signal. Failures use the existing per-peer exponential back-off. A session that runs over the DHT is replaced by a LAN/saved-address one when such a dial works (tried every 60 s; `runSession` ranks "not dht" above "dht" on both ends, then the smaller initiator id, so there is never a duplicate session). `members`, replication, proxies, media: unchanged.
- **Lifecycle.** `syncDht()` (serialised) starts the node when `enabled && group && !revoked && !paused`, restarts it when the bootstrap list or group changes, stops it on pause / leave / revoke / dispose (all DHT sockets destroyed, server unannounced, node destroyed). Start failures back off 10 s .. 5 min; "not available" retries every 10 min. Network changes (the interface/address set is compared every tick, 10 s) call `server.refresh()` / `dht.refresh()` to re-announce. The node is HyperDHT's default (ephemeral until proven reachable, so a phone behind mobile NAT does not become a routing node).
- **Settings** (ledger kv `dht` = `{enabled, bootstrap[]}`, RPC `syncSetDht {enabled?, bootstrap?}`, status `dht {enabled, bootstrap, state: off|starting|ready|unavailable|error, reason, publicKey}`): the switch and "Use my own bootstrap node" (host:port list, max 5, validated; empty = the public Holepunch bootstrap nodes).
- **What the DHT / bootstrap nodes can see (threat model).** Your public IP address and port, the IP of the peer you connect to, timing, the fact that you run a UniChat-style HyperDHT node, your device's DHT public key and that it announces it / looks up the other devices' keys (a stable pseudonym per group and device; two groups of the same person are unlinkable by key). They do NOT see: the group id, the group key, device ids or names, the Noise keys (the DHT key is a one-way HKDF derivation; there is no topic or hash derived from the group id in clear), pairing codes (never sent over the DHT), or any content (the DHT stream is end-to-end encrypted by HyperDHT's own Noise, then our Noise runs inside it). A DHT node can drop or delay traffic (DoS, like a relay) and, if it controls many nodes around a key, learn WHEN a device looks up a specific key. Anyone who learns a member's DHT public key (a former member, who still knows the old record) can look up that key's current IP address: revocation therefore removes the key from the firewall, but cannot hide an address that was already known; use "Use my own bootstrap node" for a private DHT (the bootstrap list is the only entry to a DHT, a separate list = a separate network). **A bootstrap node of your own makes the whole thing independent of the Holepunch network.**
- **Pairing over the DHT (added 2026-11-16, for networks where nothing local works, e.g. a university network; `pairingDhtSeed` in `dht.ts`).** The device that SHOWS a code also listens, for as long as the code is open, on a HyperDHT key derived as `HKDF(pairingPsk(code))` (the scrypt key of the code, so each guess costs ~0.1 s / 32 MB, the same price as attacking a recorded handshake); the device that ENTERS the code connects to that key, in parallel with the LAN candidates, and the first authenticated handshake wins. The DHT only carries bytes: the Noise_XXpsk0 handshake with the code psk and the 6-digit comparison on both devices stay the authentication, the `pair` mode is the only one the pairing key accepts (never `nearby`, never `sync`), and no pairing is accepted once the code is closed (the node lingers 90 s so a running handshake can finish). Residual risk, accepted: an observer of the DHT sees the announced key for the code's lifetime (5 min, single use) and could try guesses offline; with 2^50 codes at ~0.1 s per guess that cannot finish before the code is dead, and a correct guess still needs the live handshake and both users' digit comparison. There is no per-source lockout for DHT callers (no address), only the 8 unauthenticated sessions cap and the global wrong-attempt limit. After pairing the two devices hand each other their group DHT keys (`welcome` / `joined` frames), so they find each other over the internet without ever having shared an address. A PAKE (CPace/OPAQUE) would still be better: it would remove the offline-guess surface completely.
- **What is verified:** with an in-process local testnet (hyperdht/testnet on 127.0.0.1) only: two SyncServices with different data dirs, no LAN address, sync over the DHT, reconnect, refresh, non-member / revoked key refused at the firewall, LAN preferred and no DHT socket opened when LAN works, DHT session upgraded to LAN, clean stop, "not available" fallback, key derivation and settings (`dht.test.ts`), the bundle + loader under Node 18.20.4 over the testnet (`apps/android` `--dht-smoke`). **Real internet NAT traversal (different NATs, CGNAT, symmetric NAT, mobile data) is NOT verified**; HyperDHT falls back to its own blind relay for some NAT combinations (`blind-relay` is a dependency) which are not tested here.
**Removing a device (group-wide).** Removal is a tombstone in the group state (`Dev.revoked` + `revokedBy` + `removedAck`, merged monotonically, so an old `members` list never resurrects a device) plus a fresh key that excludes it. It travels in the authenticated, encrypted `members` / `keys` frames to every connected member at once and to the others on their next session (any path: LAN, DHT, relay); each member then closes its session with the device, forgets its addresses, relay permissions and offers. A removed device that still knows an older key may complete the handshake only to be refused: the member sends `bye{why:"revoked", by}`, the device answers `unlinked` (which sets `removedAck`; until then the UI shows "removal pending for X (offline)") and unlinks itself (group key, membership and identity wiped, a new identity is made so it needs a fresh pairing; archive and account logins stay; `removedNotice` in the ledger kv shows "removed from the sync group by X"). Leaving a group of three or more writes a self-tombstone and sends it to connected members. **Group of two:** removing the other device, or leaving, first sends `unlink` over the session and waits for `unlinked` (`unlinkWaitMs`, default 5 s) before wiping; if the peer is offline the instruction is kept (`unlinkPending` in the kv, status `unlinking`, the group stays intact) and is delivered on the peer's next session; "Unlink anyway" (`syncLeave{force}`) gives up waiting. A device left alone by concurrent removals unlinks itself. Tests: `removal.test.ts`.

**Relay (optional, self-hosted)**: `UNIMSG_RELAY=1 PORT=8780 HOST=0.0.0.0 pnpm --filter @unimsg/server relay` (or `UNIMSG_RELAY=1` on `main.ts`; no Hub, no data dir), put TLS in front (Caddy/nginx `reverse_proxy` with WebSocket) and enter `wss://relay.example.org/relay` on both devices (Sync devices > Beyond the local network). Devices meet in room `HMAC(group key, sorted device ids)` (only members can compute it, it changes when a device is removed); the device with the smaller id waits in the room, the other dials; the relay pairs two sockets and copies binary frames (no accounts, no storage, rooms vanish; limits: rooms, connections and rate per address, message size, bandwidth, idle). It sees the 1 KiB plaintext prologue (protocol, key tag) and ciphertext only; it can drop or delay traffic, not read or alter it undetected. Pairing itself still needs one direct connection (code + digits).

**Sending through another device (automatic home-device proxy; user words: "via <device>").** Signal/WhatsApp sessions cannot be copied, and the user may want a login on one device only. The device that **holds** the live login (A, e.g. laptop) answers `proxy.call {acct, op, args}` (allow-list `PROXY_OPS`, native ids; A prefixes the account itself) for a paired device B (e.g. phone, which only has the account as a mirror) **only if A's user allowed it**. Allowed means either the per-account switch "Let my other devices send as this account" (default OFF, Advanced) or a remembered per-device answer (`relayDecisions` in the ledger kv; true/false; false beats the switch). B asks on demand (`relay.ask`, from the composer / account card button, never automatically); A shows ONE prompt "Phone wants to send messages as Mattermost through this device. Allow?" (`syncStatus.proxy.asks`, `RelayWatcher` in the UI), the answer is kept per device and account and listed / revocable in Sync devices (`syncRelaySet {deviceId, accountId, allow: true|false|null}`). A offers per peer `offers [{id, provider, label, allowed, denied, activeAt}]` for its live, synced accounts only (a relayed account is never offered onward). **B reconciles automatically** (`Proxies.reconcile`): a mirror account with no own live connector and an online, allowing holder gets a `RemoteConnector` (`auto: true`; `syncUseProxy` remains as a manual pin, `syncStopProxy` = "do not pick it up again"). Holder choice is deterministic and does not flap: keep the current holder while it is online and allows; otherwise the online allowing holder with the newest `activeAt` (last message/receipt/relayed call), ties by smaller device id. If B has its own live login it never relays; a device never relays through itself. Capabilities = the holder connector's (`info` op). The Hub shows `Account.via {kind: relay|offline|ask|denied, device}` (SyncHostApi.annotate); `relay.ts` in the UI fixes the wording: "via MSLaptop" (state connected, green), "Archive only — MSLaptop is offline", "History copy — ask MSLaptop to allow sending" / "... doesn't allow sending". Offline: the connector reports disconnected, writes are **rejected** with "<device> is offline ..." (no queue, nothing replayed on return; a failed send keeps the usual Retry); the connection resumes by itself. Security: only paired non-revoked devices (the session proves it, `paired()` re-checked); revoking a device deletes its answers and ends its relays; writes (send, react, edit, delete, vote, group/space management) are rate limited per device (30 per 10 s, `SyncOptions.relay`) and the audit (`syncStatus.devices[].audit[acct]`: counters + last 20 writes `recent`) is the only place a "sent from <device>" shows; chats carry no tag. Session files, keys and login prompts never cross; events `ev` never carry login prompts/errors. Attachments up to 64 MB. **Writes happen once (idempotency).** Every relayed write carries a request id (`proxy.call {…, rid}`; `PROXY_WRITE_OPS` in provider-remote). For `send` the id is the app's `clientId` (random 128 bit, made by the UI when the message is first sent and kept in the failed-send payload, so **Retry sends the same id**; `OutgoingMessage.clientId`, `Hub.send`); other writes get a random id per call. The holder keeps results per (device, id): 10 min, 500 entries per device (`SyncOptions.idem`), memory only for results; a repeat returns the cached result, a repeat while the first try still runs waits for it (single flight); only successes are kept, a failed write may be tried again. For **sends** the holder also persists a tiny reference in the ledger kv (`relaySent`: request id -> chat id + message id + time, never the text) written before the service is called and completed after, so a retry after a holder restart returns the original message (rebuilt from the holder's archive); a reference without a message id (the holder died mid-send) answers "cannot tell if it went out. Check the chat before you send it again." until it expires. Rate limit and audit apply to executions, not to answered repeats.
**Scheduled messages.** The schedule lives on the device where it was made and fires there (job kind `send`, payload `{chatId, text, clientId, due}`, `Hub.runScheduledSend`). For a relayed account: holder offline -> `JobWaiting` (job stays pending, `payload.waiting`, `lastError` "Waiting for MSLaptop to come online", nothing counted as a failed try; polled every 30 s and woken at once by the account's `connected` event), then it is sent once with its clientId. Too late (setting `scheduleLateHours`, default 24 h, measured from `due`; applies to every scheduled send) -> `JobAbort(late)`: failed with "...could not be sent within 24 hours, so it was not sent. Send it now or delete it."; `sendJobNow` (the user's decision, still idempotent) or `discardJob`. Holder no longer allowing / account no longer connected here (holder removed, or this device removed by the holder: the holder sends `bye{why:"revoked"}` and the phone drops its relays) -> failed at once with the reason. UI: Settings > Scheduled messages (Waiting / Not sent cards) and a note above the composer.

**Wire.** `members{devices,keys,ledger,port,addrs}`, `have{of,cursor,empty}`, `batch`, `keys`, `snap-*`, `rpc/rpc-res`, `big` (chunked JSON, caps), `ev`, `offers`, `sub`, `ping`, `bye`; frames <= 512 KiB, ChaCha20-Poly1305 with counter nonces.

**Threat model.** Protects against: passive/active LAN attackers (Noise + psk, SAS, per-source lockout), a stolen/removed device (revocation re-keys; its sessions are closed), a malicious relay (ciphertext only), a curious peer for accounts set to "Don't sync" (nothing leaves, also no blobs). Does NOT protect against: what the optional HyperDHT transport necessarily reveals to DHT nodes (IP addresses, timing, a pseudonymous per-group device key: see "Reach my devices from anywhere"), a compromised paired device (it holds the archive and can use proxied accounts while online), someone who sees the pairing screen and the code AND confirms the digits themselves, traffic analysis (a relay sees who talks when and how much), a user who exposes the sync port to the internet by choosing a public address (document: use VPN/DDNS knowingly). `sync.db` holds hashes of media and the sealed device key/group keys (sealed with the archive key; with `UNIMSG_DB_KEY` unset the key file sits next to it, like the archive).

**Upgrade from phase 1.** Sync was disabled with an identity only on the real backend, so nothing migrates: the identity and any `group` row are read as before (a stored single `addr` is moved into `addrs`; an old group keeps working, the listener simply stays closed until "Sync over the network" is switched on). The `listen` setting did not exist: no device listens after the upgrade until the user opts in; devices paired in phase 1 need one device with the listener on. Ledger rows are compatible (messages without reaction elements are read as "elements stamped r"). Restart the backend after the update.

**Move session, file fallback (one-time packages).** `exportData` with `sessions` writes a random `transferId` into the manifest; the importer refuses a package whose id it already imported (`importInspect` reports `alreadyImported`), dismissing the moved account makes the package usable again. A package is a bearer token: two DIFFERENT installs importing the same file cannot be prevented without a server (the source wipe is what keeps one owner, so confirm the source wiped first). `moveAwayAccount` now reports a failed wipe instead of silently leaving session files behind.

**Move to another device (device to device, `packages/sync/src/move.ts`).** The main path of Settings > Move to another device. The login of ONE account goes from this device to a PAIRED, online device over the same authenticated Noise session as sync, in two phases. Frames are `mv-*` with `mv: 1` (unknown versions are refused with a reason, never acted on) and are point to point only: they are never written to the ledger, never replicated to a third device and never logged; the persisted records (ledger kv `moves`) hold metadata only. The file export/import below stays as the offline fallback ("Use a file instead").

```
 source (OUT)                                          target (IN)
 asking      --mv-prepare{acct,provider,label,sizes}-> asking    user sees "Move X from A to B?"  (no secrets sent yet)
             <-mv-reply{ok | reason}------------------ staging   accepted: sealed staging area, NOT active
 sending     --mv-begin{files[rel,size,sha256]}------> 
             --mv-chunk{f,i,b64} x N (192 KiB)------->            per-file SHA-256, strict order, size caps
             --mv-end{manifest sha}------------------> staged     manifest verified
             <-mv-staged{ok}---------------------------
 committing  --mv-commit-----------------------------> committing install (write files, importSession re-seal,
             (point of no return for cancel)                         start the connector, wait until it leaves "connecting")
                                                       owned      record written durably BEFORE the answer leaves
             <-mv-done{ok} ---------------------------           | aborted (rolled back: files, account row restored)
 wiping      stop connector + wipe session, NO remote logout (Hub.moveAwayAccount); record "wiping" first so it never runs twice
 done        --mv-ack---------------------------------> (nothing left to clean)
 failed      any error / cancel / timeout / disconnect BEFORE the target is "owned": target staging removed, source untouched
```

Who owns the account (invariant checked after every scenario in `move.test.ts`):

| moment | source | target |
|---|---|---|
| asking, sending, staged | owner | nothing installed (staging only, sealed, no connector) |
| after `mv-commit` is sent | still running, state `committing` (outcome unknown) | installing |
| target recorded `owned` | running until it learns this (short, both live) | owner |
| source got `mv-done{ok}` or `mv-state{owned}` | wipes exactly once, then `done` | owner |
| target install failed (`mv-done{ok:false}`) | owner, `failed` with the reason | rolled back, `aborted` |

Failure rules: (1) nothing is installed before the target user confirmed AND the whole manifest verified; (2) a lost connection, cancel (either side), timeout, tampered/damaged chunk or refusal before commit rolls the target's staging back and leaves the source untouched; (3) if the answer is lost after commit the source stays `committing`, asks `mv-query` on every reconnect and on a timer, and the target's answer is binding: `owned`, or `not-owner` after which that transfer id is tombstoned and can never commit; (4) the source wipes only after it has seen `owned`, never before, never twice, and never with a remote logout; (5) a transfer id works once: any `mv-prepare` with a known id is refused (`replay`), moving back is a new transfer in the other direction. Receiving: only devices of the sync group (paired, not removed) can send; the receiving user must confirm (no silent accept); one incoming move at a time; at most 5 prepares per device per 10 minutes. The target refuses accounts that are signed in there, provider kinds it cannot run, and oversized sessions (512 MB / 4096 files / 128 MB per file). Staging is AES-256-GCM sealed with the install's seal key next to `sync.db` (memory when there is no directory) and swept at start-up. The target connector failing to start is reported to the source and the move is rolled back, so the source stays the owner. Limits of the design: with two parties and no server the short window between "target owned" and "source learned it" has both connectors able to run; it closes on the next message or reconnect (the source never restarts a `committing` account). A target that crashes between installing and writing its record is resolved from disk when the source asks (active account row = owned).

**Several accounts, history copies, relayed copies (2026-11-14).** `syncMoveStart{accountIds:[...], deviceId, confirmed:true}` (or the single `accountId`) creates one transfer per account (`MoveRec.batch {id,n,i,items}`; rows start `queued`) and runs them one after another over the same connection; every transfer is the full PREPARE/TRANSFER/COMMIT above with its own transfer id and its own exactly-one-owner guarantee. One failure does not stop the others (that row is `failed` with its reason, the next one goes); a cancel stops the remaining rows and rolls back only the one in flight (rows already `done` stay done); a refusal of the whole batch (`denied`) fails all remaining rows; a lost connection fails the rest ("nothing changed") while an unknown-outcome `committing` row is resolved by `mv-query` as before. The target is asked ONCE: the first `mv-prepare` of a batch carries the full item list and shows one dialog; `syncMoveRespond{transferId, accept, accountIds?}` answers for the batch (unticked accounts get `skipped`), later prepares of that batch from the same device are accepted without another prompt, and the rate limit counts the batch once. The target refuses only an account it has its OWN login for (`ownLogin`: a live connector that is not a relay, an active account row, or session files on disk). A history copy (archive row, mirrored chats) or a copy used through the source (relay) is replaced: before the install the relay is detached (`Proxies.stopUsing`), `Hub.moveInstall` keeps the row's history and chats, installs the session over it and flips the row to active; on any failure the previous row and files are restored (the relay is not re-attached automatically). `syncStatus.accounts[]` carries `canMove` and `moveWhy`.

**Chat history with the move.** `syncMoveStart{…, includeHistory (default true), includeMedia (default true), removeHistoryAfter (default false)}`. After the login is staged and verified, and BEFORE `mv-commit`, the source streams the account's archive point to point (`mv-hbegin`, `mv-hrows` batches of messages / chat list / link events / names / flags / folders, `mv-hfile` + `mv-hchunk` for each cached attachment with a SHA-256, `mv-hend` with the counts). It is read from the store restricted to that one account (`packages/core/src/history.ts`: `historyPieces`, `historyEstimate`) and applied on the target with merge semantics (what is newer there is kept; messages merge by id), so it is idempotent and works whether or not ordinary sync already delivered part of it. The target verifies per-file hashes and that the message and file counts equal what was sent, then answers `mv-hdone`; frames are applied one at a time and the receiver does not read the next frame before the previous is applied (backpressure, bounded memory). Rule: the commit of the login and the source's wipe happen only after `mv-hdone{ok}`. A history failure (error, lost connection, lost `mv-hdone`, timeout) ends the move as `failed` with `histFailed`: the source stays the owner, nothing is committed or wiped, and the UI offers "Move without history" (a new move with `includeHistory:false`); history rows the target already merged simply stay as a history copy there. The source keeps its archive unless "Remove the history from this device afterwards" is on; then, only after the target confirmed ownership and the wipe ran, it deletes the account's messages and cached files locally and sets the account's sync mode to "none" so ordinary sync does not bring the history back (local deletion only: no tombstones go to other devices). `syncMoveEstimate{accountIds, includeMedia}` returns messages / files / bytes for the confirm dialog ("About 540 MB: 88,000 messages, 9,300 files"); progress rows show messages x of y and MB. `syncSendHistory{accountId, deviceId}` is the same history phase alone (kind `history`, no login, no commit): the receiver confirms, the archive is merged, nothing is wiped.

**Where history comes from (answer to "Fetch chat history").** Settings > Storage & downloads > "Fetch chat history" asks the messenger's servers or phone for older messages; it never pulls from paired devices. Paired devices already replicate each other's archives through normal sync: per account the mode "Sync history only" (archive-only) or "History and login" (credentials) keeps messages, edits, reactions, flags and names in step automatically, in both directions. To bring an old archive to another device: (1) just pair the devices and keep the account on "Sync history only" (automatic, the initial transfer is a snapshot); (2) Move to another device with "Also move the chat history" (one account, login + archive, optionally removing it here); (3) Advanced > Sync devices > "Send the full history of <account> now" for a one-off push of one account to one device; (4) Backup & restore for a file. 

**Origin of an account (no sharing chains).** An account that was only shared TO this device (credentials adopted from a peer: ledger kv `origins[acct] = deviceId`, set when the user accepts the login; a history copy with no login here; a relayed account) reports `syncStatus.accounts[].sharedFrom = <device name>`. For those the credential option and the "let my other devices send as this account" switch are hidden with "This account comes from <device>; share it from there." and refused server-side (`setMode('credentials')`, `syncSetProxyShare`, `syncRelaySet allow:true` throw "This account comes from X; share it from there."); the credential sender (`refreshCreds`/`collectCreds`) and the relay holder (`Proxies.liveHere` via `blocked`) skip them, and adopting credentials resets a leftover "credentials" mode to history-only. An account the user MOVED here has no origin (cleared on commit): it is their own login and can be shared.

Backend API (all `sync*` methods of the service): `syncMoveStart{accountId, deviceId, confirmed:true}`, `syncMoveRespond{transferId, accept}`, `syncMoveCancel{transferId}`; `syncStatus.moves[]` (role, from/to names, phase `confirm|waiting|sending|finishing|done|failed`, progress, plain-words error) and `accounts[].canMove`. Hub primitives: `SyncHostApi.moveCollect` (portable session via the provider hook) and `moveInstall` (atomic: on any failure the previous archive/files are restored). Tests: `packages/sync/src/move.test.ts` (real Hubs paired over loopback, fake provider: happy path with a third paired device and secret scan, deny/cancel both sides, disconnect at prepare/transfer/commit/answer/ack, lost answer, tampered chunk, connector failure, moving back, replay, 20 MB session, guards), `packages/core/src/movecore.test.ts`, `android.test.ts`; UI: `apps/ui/e2e/tests/move.ts` against `mockSync.ts`.

## Avatars (persistent + synced)
- `Hub.avatar(kind, id, full)` resolves: in-memory cache (hits 6 h, misses 10 min) -> durable store -> live connector (3 at a time). The Store keeps one row per `kind|<global id>[|full]` in one of three states: a picture (mime, sha-256, bytes, fetchedAt, provider hint `rev`), `empty` ("the provider has none", remembered 1 h) or `gone` (a tombstone with the deletion time). `SqliteStore` seals mime/hash/hint/bytes with the data key; account id, time and size stay readable for deletion and eviction. Limits (`core/avatarstore.ts`): 256 KB per picture (larger ones are shown but not kept), 64 MB in total (oldest fetched first out), tombstones 30 days, other rows dropped after 120 days. A failed or empty refresh keeps the stored picture.
- Freshness: a provider hint (`Chat.avatarRev` / `Space.avatarRev`, any opaque string; otherwise a hash of `avatarUrl`/`iconUrl`) that differs from the stored `rev` refreshes the picture at once, a matching hint is trusted for 30 days; without a hint the TTL is 7 days, 24 h for a chat opened in the last 7 days. Providers can also emit `{type:"avatar-changed", data:{id, kind?}|{own:true}}`: the Hub refreshes the stored copies immediately and emits `avatars-changed {keys}`. Own picture: `updateProfile` (and `{own:true}`) re-fetches every stored copy that has the old picture's hash (the note-to-self chat etc.), or, when the old one is unknown, marks the account's pictures stale.
- Deletions: `Store.deleteAvatars` (leaving a chat, changing a chat picture, `deleteAccountData`) turns rows into tombstones, never plain deletes, so sync can carry them. Merged chats resolve through their members as before (primary first, then the others).
- Sync (`packages/sync/src/avatars.ts`) is a pull outside the ledger: `av.list` pages `{k, s (sha), t (fetchedAt / deletion time), z (size), st: "none"|"gone", r (hint)}`, `av.get` returns one picture. Rule (`avatarWins` in core/store.ts): a tombstone beats an older or equal picture, a newer fetch beats a tombstone, a different picture needs a newer time, "no picture" (only listed while younger than 1 h) never replaces a picture and any picture replaces it. Only accounts that exist here and are not sync mode "none" are accepted (tombstones are listed for every account; the receiver applies them only for accounts it has). Rate limit: 200 pictures per run, 40 ms gap, per peer every 5 min; paused on a metered connection unless the media policy is "all". Nothing secret is involved. After applying, the Hub emits `avatars-changed {keys}`; the UI drops those entries (and every cached miss) and reloads once.
- Provider hint sources: Matrix (hash of the chat's avatar data URL, already in `avatarUrl`), Mattermost (`last_picture_update` of the other person; `last_team_icon_update` for teams), Discord (avatar / group-icon / guild-icon hash), Instagram (CDN path of the other person's picture, query signature ignored), WhatsApp and Threema (linked device) via `avatar-changed` events (WhatsApp 'picture' notifications; Threema profile-picture messages). Signal (no hint API for group pictures in the client we use; DM pictures are not implemented), Teams (Graph gives no cheap hint; TTL applies), Threema Gateway (no avatars) have none.
- Warm-up and fast drain: a device with live connectors fills its avatar store in the background (`Hub.warmAvatars`, RPC `avatarWarm` to run it now, `setAvatarWarmPaused {paused}` for hosts to pause it on a metered connection / low battery): after a connect (30 s) and every 6 h it fetches all spaces/communities first, then chats in local folders, then the 300 most recently active chats, through `avatar()` (so only missing/stale pictures, the hint/TTL rules and the stored "no picture" are honoured), one provider request per 400 ms, at most 3 in flight with UI requests, exponential back-off on errors and a stop after 5 in a row. Because the store is what sync serves, pictures nobody scrolled to now reach the other devices. Sync side: a pull that moved anything schedules the next one 15 s later (repeat until a pull moves nothing, then the 5 min rhythm), the holder sends a small `av.hint` rpc when its store changed outside a pull (throttled to once per 10 s, never echoed for pictures it just received) and the receiver pulls ~0.5 s later, still subject to the metered rule. On a device without a connector the UI re-requests every cached miss (spaces included) on `avatars-changed`.

**Following the network (2026-11-15; `service.ts` `networkChanged`, `learnAnnounced`, `group.ts` `applyAnnounced`, `addrs.ts` `netFingerprint`).** A paired device listens on the local network by default (well-known port 45045..45052; Android: one wildcard socket, inbound connections not on a private address are dropped). Whenever the interface set changes (the Android connectivity callback `$network`, or the 10 s tick noticing a different address list) the device re-binds listeners, re-joins mDNS multicast, refreshes the DHT node, closes sessions that ran over a vanished local address, clears all dial back-offs and sends `{t:"addrs", port, addrs:[{kind:"tcp",host,port,net}]}` over every live session; the same list is part of the `members` frame that starts each session, so it also travels through a DHT session. Receivers treat the list as authoritative for second-hand addresses (learned / mDNS / pairing): addresses not in it are dropped (a peer that left its home Wi-Fi is no longer dialed at the old IP; manual addresses stay; an empty list changes nothing) and each address carries the owner's network fingerprint (hash of its private subnets). If the peer is currently connected only through the DHT or a relay, the new addresses are tried directly at once (1.5 s connect timeout, own-subnet addresses first) and the session migrates to the direct path (one session per peer: the existing tie-break); when the direct path breaks the normal dial (tcp, then DHT) brings the DHT session back. Not implemented: a signed DHT mutable record with the addresses for peers without a session (the DHT connection itself is the channel; a record would need its own group-encrypted format and testnet coverage). The device row shows `viaKind` (Direct (Wi-Fi) / Through the internet (DHT) / Via relay).

## Updates (packages/core/src/updater.ts)
Every push to `main` publishes a GitHub pre-release `v0.1.<run number>` (`.github/workflows/release.yml`). Besides the artifacts it carries `latest.json` (written by `scripts/release-manifest.mjs`): `{version, publishedAt, notes, assets: {android | desktop-linux-appimage | desktop-linux-deb: {name, size, sha256}}}`.
- **Version**: CI sets `UNICHAT_VERSION` (0.1.N). It reaches the UI (Vite define `__UNICHAT_VERSION__`), the desktop package version (`electron-builder -c.extraMetadata.version`), the Android versionName and the Android backend bundle (esbuild define). Local builds are `dev` and never offer an install.
- **`Updater`** (one per Hub; RPCs `updateCheck/Status/Download/Cancel/Install/Settings`, events `update-available`, `update-progress`): lists the repo's releases through the GitHub API (default `PixelcrafterEXE/unichat`, pre-releases allowed), takes the highest `v0.1.N` that has a `latest.json`, compares numerically, downloads the asset of its platform to `<data>/updates/` (resumes dropped connections with Range, one download at a time, partial files are always removed), verifies size + SHA-256 from the manifest (mismatch = refused and deleted), then installs through the platform hook. Background check 15 s after start and every 6 h while "auto" is on (not for dev builds, not on metered connections, backs off after a 403/429).
- **Private repo**: an optional read-only token (Settings > About > Updates > Advanced). It lives in `<data>/updater.json` (AES-256-GCM with a key derived from the data key, mode 0600), not in the synced store, is never returned or logged, and is sent only to the API host: asset downloads follow the redirect to the CDN without the `Authorization` header. No token = anonymous requests (works once the repo is public).
- **Installers**: Desktop AppImage: the verified file replaces `$APPIMAGE` by rename (old one kept as `.bak`) and the app relaunches (`apps/desktop/src/updater.ts`); .deb: shows the file, install by hand. Android: `updateInstall` answers `handoff`, the UI calls the native `$installApk` (`NodeBridge`), which accepts only files under `files/unimsg-data/updates`, opens "install unknown apps" if needed and starts the system installer through the FileProvider. The CI APK is signed with the developer's debug keystore (secret `ANDROID_DEBUG_KEYSTORE_B64`), otherwise Android rejects the update. Web/server: only "a new version is available".
