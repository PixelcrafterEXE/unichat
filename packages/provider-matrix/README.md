# @unimsg/provider-matrix

Matrix provider on `matrix-js-sdk` 45.0.0 (classic `/sync`, Rust crypto via `@matrix-org/matrix-sdk-crypto-wasm`). Requires Node >= 22.

## Design
- **Login**: form (homeserver, username, password). Homeserver may be a bare domain (`.well-known` discovery) or URL. Leaving username and password empty starts SSO: a `link` prompt with a loopback redirect (127.0.0.1, random port) - works only when the browser runs on the same machine as the Hub. Session (`matrix-session.json`, 0600) is restored on restart, no re-login. `M_UNKNOWN_TOKEN` / soft-logout -> wipes session, emits `needs-login` and a new form prompt. Other sync errors -> `disconnected`, the SDK retries with backoff.
- **Stores**: sync store is `MemoryStore` (each start does an initial sync with lazy-loaded members; unread counts come from the server). Crypto store: Rust crypto supports only IndexedDB or memory, and Node has no IndexedDB, so it runs on `fake-indexeddb` and `idb-persist.ts` snapshots the `unimsg-<accountId>*` databases to `matrix-crypto.bin` (every 10 s if changed, on stop, atomic write, 0600). The crypto DB is itself encrypted with a random per-session key (`cryptoKey` in the session file - protects against casual disclosure of the snapshot only; the key sits next to it). Crash loses at most ~10 s of new Olm/Megolm state. Chosen over memory-only (new device and lost keys each start) and over native sqlite (not supported by the Rust SDK wasm build).
- **E2EE**: rooms are encrypted when the server says so; new DMs/groups are created encrypted. Encrypted attachments implemented in `attach-crypto.ts` (AES-256-CTR + sha256), since the SDK ships none.
- **Verification** (emoji/SAS, cross-signing set-up, recovery-key verification) is implemented in `src/verification.ts` behind the generic `verification` contract of core (see "Verification" below). It is only fake-verified. Until a device is verified the device appears unverified to others (Element shows a warning shield); this client sends to unverified devices (SDK default, no blacklisting); history encrypted before this device existed is shown as placeholder text unless the key backup is restored; keys requested from other devices are only shared if those devices trust this one. Late-arriving keys update the message text via `message-update` (attachments are not patched).
- **Mapping**: room id = chat id, event id = message id. DMs = `m.direct`; rooms listed as `m.space.child` (with `via`) of a joined space -> `channel` with `spaceId`; other rooms `group`; spaces themselves are only in `spaces()`. Nested spaces appear flat.
- **Events**: live timeline events after the initial sync -> `message` (backlog is served by `history()`); edits/redactions/reactions -> `message-update`; read receipts of others -> `receipt`; typing; `chats-changed` (debounced); `spaces-changed`; account state; `error` (error codes only, never content/tokens).
- **history()**: `/messages` backwards; `beforeMessageId` resolved via `/context?limit=0`. Edits use bundled `m.replace`.
- **Avatars** are fetched with the access token (authenticated media) and returned as small `data:` URLs.

## Not done / TODO
Starting a new thread from UniChat (replies to thread messages stay in their thread, but there is no way to open one); sending formatted text (sending is always plain `body`, plus pills for mentions); outgoing images have no width/height/thumbnail; muted state; redacted edits do not revert text; nested space hierarchy via `/hierarchy` and `m.space.parent`; refresh tokens / OIDC (MAS) login; contact cards (no Matrix standard); `forwarded` ignored.

## Verified against a real homeserver (Synapse 1.165.0)
Suite: `lab/synapse.e2e.ts` (25 steps, about 80 s), driving the real `ProviderFactory` / `Connector` code (temp data dirs) as alice, bob and carol (bob and carol are further provider instances; protocol-level extras such as ending a poll or joining an invite use the SDK client behind a connector). Homeserver: throwaway Synapse in a Python venv, sqlite, listener on `127.0.0.1:8008` only, no federation, no TLS, registration only via shared secret, rate limits lifted, fake users `alice`/`bob`/`carol` (`<name>-lab-pass-1`), server name `lab.test`. `lab/run.sh` (= `test:synapse`) creates the venv (`pip install matrix-synapse`, needs network once), wipes the database, starts Synapse, registers the users, runs the suite and stops Synapse again. `LAB_DIR` (default `$TMPDIR/unimsg-matrix-lab`) and `PORT` can be overridden; `lab/synapse-lab.sh setup|start|stop|restart|reset|status|users` controls the server by hand. The harness refuses non-loopback homeservers.

Verified (all passing):
- password login (localpart and full mxid), failure messages (wrong password, unknown user, empty homeserver, one field only, unreachable server, no-SSO server), session file mode 0600, no login prompt with a stored session
- initial sync: chats()/spaces() (kind dm/group/channel, names incl. DM peer name, topic, preview, lastMessageAt, readOnly, unread counts from the server), nothing from the backlog emitted as live messages, restart with the persisted session
- history(): paging backwards with `beforeMessageId`, ordering, no duplicates across pages, decrypted history in encrypted rooms
- send/receive text in an encrypted DM, an encrypted group and an unencrypted room; replies (reply preview), edits (live + history, only own), deletes (redactions, also in encrypted rooms), reactions add/change/remove (live + history), typing (and typing privacy off), read receipts incl. private receipts, markRead clearing unread
- attachments: image, file and voice (MSC3245 flag + MSC1767 duration and waveform, 64 bars preserved) as upload/download round trip in unencrypted and encrypted rooms (own `attach-crypto.ts` against Element-style `file` objects, bytes compared), live and via history; location
- polls (stable MSC3381 events): start, vote from bob and alice, changed vote, max selections, end (by a user with redact power), vote after end rejected, tally from history, encrypted and unencrypted
- spaces: createSpace, adding rooms (`m.space.child`) shows up as `spaceId` / kind `channel`, invite + joinSpace (room id, matrix.to link), refusing a non-space, refusing without invite, leaveSpace (children stay joined)
- startChat (encrypted DM, idempotent), createGroup, addMembers (bare localpart expands), removeMember, renameChat, setChatPicture (set/clear) + avatars of chats/contacts, leaveChat, blockChat/unblock (ignore list; the server really stops delivering the user's messages)
- profile display name + avatar (set/clear, propagation to other users), privacy settings as account data (survive restart)
- E2EE: encrypted DM/group send and receive, devices stay unverified and nothing blocks, no key backup active, crypto store persisted across a provider restart (same device id; decrypts messages sent while down and after the restart, history decrypts, can send again)
- logout (local wipe, access token dead, device removed server-side, re-login with the same account id in the same process), session revoked elsewhere (`needs-login` + new prompt, files wiped), reconnect after the homeserver was restarted (no `needs-login`, traffic resumes)
- invites: a pending invitation is a `Chat` with `request: true` (DM invites `kind: dm` named after the inviter, room invites, space invites); `acceptRequest` joins (and records DMs in `m.direct` like Element), `declineRequest` rejects the invite, sending to a request accepts it first, a withdrawn invite disappears, `history()` of a request is empty
- mentions: `OutgoingMessage.mentions` become `m.mentions` + `org.matrix.custom.html` pill links (`https://matrix.to/#/@user:server`); plain text without mentions stays a bare `m.text`; receivers (provider) show `@Name`
- formatted bodies: `org.matrix.custom.html` rendered to readable text (`**bold**`, `*italic*`, `~~strike~~`, `` `code` ``, fenced code, `- ` / `1. ` lists, `> ` quotes, `text (url)` links, `@Name` pills, `||spoilers||`), `<mx-reply>` and body reply fallbacks stripped, also for edits and via `history()`; sender-supplied MSC4095 link previews (`com.beeper.linkpreviews`) become a `link` card (we never fetch URLs)
- threads: `m.thread` replies map to `replyTo` (target = real `m.in_reply_to` or the root) with an extra `thread: true` field on `replyTo`; answering a thread message (or a thread root with bundled thread info) sends `m.thread` with `is_falling_back: false`, so it stays in the thread in other clients
- key backup restore: optional "recovery key or passphrase" field on the login form (restore runs after the first sync; wrong key = connected + `backup-restore-failed` error event), or privacy-settings entry `keyBackup` ("Restore with recovery key or passphrase...") which opens a form prompt; accepts Element's security key (secret storage), the raw backup key, the secret-storage passphrase and the legacy backup passphrase. Verified: first device creates a backup, second/third/fourth logins read history that predates them (also after a restart: the backup key stays in the crypto store); wrong keys are rejected. Read-only `deviceVerification` entry shows whether this device is cross-signed (verified after another client set up cross-signing)
- room description: `setChatDescription` sets the topic, `Chat.description` follows topic changes (`chats-changed`)

Bugs found by this run and fixed (offline regression tests in parentheses):
1. matrix-js-sdk's module-level logger ignored the per-client silent logger and printed HTTP traces with room ids to stdout (persist.test.ts).
2. After PREPARED the SDK still delivers the initial sync's room timelines (and, for a freshly joined room, its whole history) as "live" events: old messages and system rows were emitted as new messages. Now events older than the connector's start (server clock via the `Date` header, +-0.5 s), repeats, and the pre-join history of a newly joined room are dropped (connector.test.ts). Consequence: a new message that arrives within about 0.5 s of connector start may be treated as backlog (history() still has it).
3. Deleting a message in an encrypted room produced no `message-update {deleted}` (the redacted event loses its clear type and reports `m.room.encrypted`); lab suite only (needs a real encrypted redaction).
4. Polls could only be ended by their creator; MSC3381 also allows anyone who may redact (room admins). `tallyPoll` takes `canEnd` (map.test.ts).
5. joinSpace() with a room v12 id (`!opaque`, no `:server`, Synapse default) was rejected as "not a space link" (map.test.ts).
6. joinSpace() of a plain room the user was already in left (and forgot) that room as "undo"; it now only undoes a join it did itself (connector.test.ts).
7. joinSpace() returned before the join membership was synced, so `spaces()` right after did not list the space.
8. createSpace()/createGroup() returned the name "Empty room" when the room reached /sync before its name state (lab suite only).
9. Logout and session invalidation: `invalidate()` re-wrote `matrix-crypto.bin` after deleting it, and the process-global in-memory crypto databases survived, so logging in again with the same account id in the same process failed to connect. `IdbPersister.drop()` deletes both (persist.test.ts).

Not verified (still): federation / other servers, SSO and `.well-known` discovery (only direct `http://127.0.0.1` URLs), OIDC/MAS login and refresh tokens, creating a key backup or secret storage or cross-signing from UniChat (the lab sets them up with the SDK; only restoring is implemented), device verification UI (SAS, QR, emoji) and signing this device, backup upload progress or large backups, threads shown as separate views (`thread` is only a hint) and starting a thread, mentions in captions/edits, @room mentions, notifications for mentions, a `thread` field in the core `Message.replyTo` type (the provider adds it untyped), rotation of Megolm sessions when members change beyond the covered add/remove, edits of attachments/redacted edits, threads, formatted bodies, Element-originated polls and voice messages (only wire shapes produced by this provider and by the SDK), calls, mentions, large uploads/media limits, authenticated media on a server that enforces it (Synapse 1.165 serves both), rate limiting (limits were lifted in the lab), other server implementations (Conduit/Dendrite), Windows/macOS.

Added by the follow-up run (all with offline regression tests where the logic is pure or mockable): `Chat.description` did not follow topic changes (`m.room.topic` now marks the chat dirty); a DM invite without a name was shown as "Empty room" (named after the inviter); the new pill rendering decodes percent-encoded `matrix.to` user ids.

## Added later (fakes only, `pnpm test`)
- **Link previews when sending** (MSC4095 `com.beeper.linkpreviews`): for the first URL in an **unencrypted** room the homeserver's `/preview_url` answer is attached to the message (best effort, 4 s timeout, `OutgoingMessage.linkPreview === false` turns it off). Never done in encrypted rooms, because it would tell the homeserver which link you posted. Element ignores the field (it shows its own preview); clients that read MSC4095 render ours. Received previews were already mapped to a link card.
- **Custom emoji** (receive): `<img data-mx-emoticon>` in formatted bodies becomes `:shortcode:` text and its `mxc://` is remembered, so `avatar({kind: "emoji", id})` can fetch the picture (`Capabilities.customEmoji`). Shortcodes are shared by all rooms/accounts of the process (a clash shows the latest picture). Reactions with an mxc key and sending custom emoji are not done.
- **GIFs**: videos with `fi.mau.gif` / `fi.mau.loop` info flags (Element) are flagged `gif`; GIF attachments are sent with those flags.
- **Disappearing messages**: Matrix has no such feature in the spec (room retention is a server policy), so the row is Unsupported.
- **Emoji (SAS) verification flow** is covered by `src/verification.test.ts` with fake `VerificationRequest` / `Verifier` objects (no homeserver): request -> Ready -> start `m.sas.v1` -> show the seven emojis -> confirm / mismatch / cancel / timeout, own device and another user (DM room), incoming requests (nothing happens until Accept), status, cross-signing set-up (UIA with password, other auth types explained, secret never logged) and recovery-key verification. The real cryptographic exchange is only testable against a homeserver plus a second device (not done).

## Verification

Generic contract (packages/core `provider.ts`): `Capabilities.verification`, event `verification` (`VerificationState`: id, phase `incoming|waiting|sas|confirming|done|cancelled`, `other` {kind device|user, name}, `emoji` as [emoji, name][], `reason`), connector methods `verificationStart({userId?, chatId?})` (no target = another device of mine), `verificationAction(id, accept|decline|confirm|mismatch|cancel)`, `verificationStatus({userId?|chatId?})` -> verified/unverified/unknown + cross-signing + backup, `verificationSetup({password?})` -> recovery key, `verificationRecover(key)`.
- Own device: `requestOwnUserVerification()`; a person: `requestVerificationDM(userId, room)` (the 1:1 room, or the `m.direct` room). Once the request is Ready we start `m.sas.v1` ourselves; the emojis come from `ShowSasCallbacks.sas.emoji` (names are the SDK's). "They match" = `confirm()` (phase `confirming` until the other side confirms), "They do not match" = `mismatch()`. A request nobody answers is cancelled after 10 minutes (`m.timeout`).
- Incoming requests (`CryptoEvent.VerificationRequestReceived`, from own devices and from other users) arrive as phase `incoming`; nothing is accepted without the user's Accept.
- Set-up: `bootstrapCrossSigning` (UIA: first without auth, then `m.login.password` with the typed password; any other flow gives a message that says which step the server wants and to use Element) + `bootstrapSecretStorage` with a new recovery key and a new key backup (only if none exists). The recovery key is returned once to the UI; neither it nor the password is stored or logged. An account that already has secret storage is not touched (use the recovery key or another device).
- "Verify with recovery key": secret storage is unlocked with the key (or passphrase) during the call only, `bootstrapCrossSigning({})` imports the cross-signing keys and signs this device (it never creates new keys when they exist), then the message key backup is loaded best-effort.
- Verification events and calls are not forwarded to proxy accounts (a remote home device); the dialog only runs on the device that holds the account.
- Pinned messages: read-modify-write of `m.room.pinned_events`, incoming state changes mark messages, `pins()` lists them. Fake-verified only.
